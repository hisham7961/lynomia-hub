## AUDIT-1 — عزلُ العميل على `/api/v1`

- **الشدّة:** P1 (أُصلِح)
- **المجال:** الأمن / عزلُ العميل / صلاحيّةُ API
- **الوصف:** مسارات `/api/v1` تعمل تحت `ApiAuth` لا `PortalGuard`، فحسابُ عميلٍ برمزِ API ودورٍ
  واسعٍ يكشف **وجودَ** وحداتٍ داخليّةٍ خارجَ قائمتِه (200 بدل 404).
- **الدليل:** `routes/api.php` (`/api/v1` تحت `ApiAuth`)؛ `V1Controller::resolveApi()` لم يكن
  يستشير قائمةَ العميل.
- **الأثر:** كشفُ وجودِ وحدةٍ داخليّةٍ لحسابِ عميل (العزلُ الصفّيُّ يمنع قراءةَ بياناتِ شركةٍ
  أخرى، لكنّ الكشفَ عن وجودِ الوحدةِ خرقٌ للعزل).
- **الجذر:** غيابُ حاجزِ نوعِ الحساب على سطحِ `/api/v1` (كان على البوّابةِ الويب/الجوّال فقط).
- **الإصلاح:** حاجزٌ صريحٌ في `V1Controller::resolveApi()` يعيد 404 لأيِّ وحدةٍ خارجَ
  `PortalGuard::MODULE_ALLOW` لحساباتِ العميل؛ رُفِعت `MODULE_ALLOW` إلى `public const` (مصدرٌ واحد).
- **اختبارُ الانحدار:** `FinalAuditHardeningTest::test_client_api_token_is_confined_to_allowed_modules`
  + `test_internal_api_token_still_reaches_modules`.
- **الحالة:** ✅ FIXED

## AUDIT-2 — اشتقاقُ حالةٍ كاذبٌ لدفاعِ IP في طبقةِ التطبيق

- **الشدّة:** P1 (أُصلِح)
- **المجال:** صدقُ سجلِّ القدرات
- **الوصف:** `security.app_ip_defense` كان `derive => 'edge'`، فيُبلِّغ «غيرَ مُهيّأ» بينما الحجبُ في
  طبقةِ التطبيق نشطٌ فعلاً — حالةٌ كاذبة.
- **الدليل:** `config/hub_features.php` (المدخلُ قبلَ الإصلاح).
- **الأثر:** كذبٌ في لوحِ القدرات يُضلّل قرارَ التشغيل (قدرةٌ نشطةٌ تظهر معطَّلة).
- **الجذر:** ربطُ حالةِ قدرةِ طبقةِ التطبيق بمِجسّةِ الحافّة الخارجيّة.
- **الإصلاح:** إزالةُ `derive`؛ صار ثابتَ `ENABLED` صادقاً. بقي `security.edge_blocking` صادقاً
  `NOT_CONFIGURED`.
- **اختبارُ الانحدار:** `test_app_ip_defense_reports_enabled_not_misconfigured`.
- **الحالة:** ✅ FIXED

## AUDIT-3 — نافذةُ رسائلِ الحاويةِ غيرُ محدودة

- **الشدّة:** P1 (أُصلِح)

- **الإصلاح:** `Conversation::rootMessages(int $limit = 300)` — أحدثُ N جذورٍ مع `with` وترتيبٍ

- **اختبارُ الانحدار:** `test_conversation_root_messages_are_bounded_and_chronological`.
