### تصحيحٌ يُسجَّل

قيل سابقاً إنّ تحميلَ `pgsql`/`pdo_pgsql` في PHP «يوحي بأنّ PostgreSQL
مستعمَلٌ فعلاً». **وهذا خطأ**: تحميلُ امتدادٍ يثبت أنّه **مُعلَنٌ في
`php.ini`** لا أنّ أحداً يستعمله — والتحذيرُ المتكرّرُ يثبت أنّه مُعلَنٌ
**مرّتين**، وهو خطأُ تهيئةٍ لا دليلُ استعمال. سُحب الاستنتاج.

## ٠٫٥) 🔴 اكتشافٌ يغيّر الصورة — منظومةُ Docker قائمةٌ لم تكن في أيِّ جرد

`docker ps -a` بـroot كشف **إحدى عشرةَ حاويةً تعمل** لمشروعٍ اسمُه
`lynomia-backend` — تطبيقُ Laravel كاملٌ **منفصلٌ عن Hub**:

| الحاوية | الصورة | المنافذ |
|---|---|---|
| `app` · `web` · `horizon` · `scheduler` · `reverb` | صورٌ محلّيّةٌ مبنيّة | داخليّة |
| **`postgres-1`** | **`postgres:16-alpine`** | `5432/tcp` داخليّ |
| `backup-1` | `postgres:16-alpine` | داخليّ |
| `redis-1` | `redis:7-alpine` | داخليّ |
| `minio-1` | `minio/minio` | داخليّ |
| `clamav-1` | `clamav/clamav:stable` | داخليّ · **healthy** |
| **`caddy-1`** | `caddy:2-alpine` | **`0.0.0.0:8080→80` و`0.0.0.0:8443→443`** — مكشوفٌ للإنترنت |

**وثلاثةُ أسئلةٍ حُسمت دفعةً واحدة:**

1. **ما المحجوز على 5432؟** حاويةُ `lynomia-backend-postgres-1`. و
   `postgresql.service` الساقطةُ **لا علاقةَ لها بشيء** — لا تُصلَح ولا تُلمَس،
   وسقوطُها لا يؤثّر على أحد.
2. **أصالحٌ Docker للإنتاج هنا؟** **يُشغّل تطبيقاً إنتاجيّاً كاملاً منذ ساعات**
   — لا تجربةَ ولا مخاطرةَ منهج.
3. **B5 جزئيّاً:** صورةُ **postgres 16** مسحوبةٌ أصلاً، فاختيارُ المِيجر نفسِه
   تناسقٌ تشغيليٌّ بلا كلفةِ قرصٍ إضافيّة.

**وقيدٌ جديدٌ على الموارد:** ١١ حاويةً + Hub + MariaDB + Webuzo على **5.9 GiB
بلا swap**. فحدودُ §٢٠ (1.5G + 768M) **تُراجَع لأسفل** بعد قياسِ الاستهلاكِ
الفعليّ (`docker stats`).

**ولوحظ ولا يخصّنا الآن:** `Build Cache 7.66 GB` منها **3.95 GB قابلٌ
للاسترجاع** — أكبرُ مستهلكٍ للقرصِ في Docker. تنظيفُه قرارُ صاحبِه.

### ❓ سؤالٌ مفتوحٌ يوقف التصميم

**ما هو `lynomia-backend` وما علاقتُه بـHub؟** منتجٌ آخر؟ أم خليفةٌ يُهاجَر
إليه؟ الجوابُ يغيّر **أين تُوضَع بوّابةُ النماذج**: بجوارِ Hub، أم داخلَ
منظومةِ backend، أم مستقلّةً عنهما. **لا يُفترَض.**

## ١) أقلُّ مجموعةِ أوامرَ لحسمِ القرار

### 🔴 ضروريٌّ — بلا هذه **لا قرار**

```bash
# (١) أيعمل Docker عبر sudo أصلاً؟ وما حجمُه ومساحتُه؟
sudo docker info --format 'Server={{.ServerVersion}} Driver={{.Driver}} Root={{.DockerRootDir}} Running={{.ContainersRunning}}/{{.Containers}}'

# (٢) ما القائمُ الآن — تضاربُ أسماءٍ أو منافذ؟
sudo docker ps -a --format '{{.Names}}\t{{.Image}}\t{{.Ports}}\t{{.Status}}'

# (٣) مساحةُ Docker الفعليّة
sudo docker system df
```

**ثلاثةُ أوامرَ لا غير.** كلُّها استعلام.

### ⚪ اختياريٌّ — يُحسّن الخطّةَ ولا يوقفها

```bash
sudo ss -ltnp | grep -E ':5432|:4000'          # مَن يحجز المنافذ
sudo systemctl status postgresql -l --no-pager | head -20   # لماذا سقطت
sudo docker network ls                          # شبكاتٌ قائمة
sudo ls -la /var/lib/pgsql/data 2>/dev/null | head   # أثمّة بياناتٌ قديمة
```

### **ولماذا سقط سؤالُ 5432 من الضروريّ؟**

لأنّ التصميمَ **لا ينشر PostgreSQL على المضيفِ إطلاقاً**: لا `ports:` لحاويةِ
القاعدة، فلا تضاربَ ممكنٌ مع المنفذ 5432 مهما كان محجوزاً. و`postgresql.service`
الساقطةُ تصير **غيرَ ذاتِ صلة** — لا نصلحها ولا نستعملها ولا نتأثّر بها.

## ٢) القرار — مرشَّحٌ أوّليّ بمبرّراتٍ من بيئتِك

| المعيار | Docker Compose | systemd + venv |
|---|---|---|
| Python 3.11 | **لا يُثبَّت** — داخلَ الصورة | `dnf install python3.11` (إضافيٌّ لا يمسّ 3.9) |
| قاعدةُ LiteLLM | **حاويةٌ معزولةٌ** لا تمسّ خدمةَ النظام | تحتاج Postgres صحّيّاً — **وهو ساقطٌ الآن** |
| لمسُ خدماتِ النظام | **صفر** | إصلاحُ `postgresql.service` = لمسُ Webuzo |
| الحدود | `mem_limit`/`cpus` في ملفٍّ واحد | `MemoryMax`/`CPUQuota` في الوحدة |
| تدويرُ السجلّات | `json-file` بحدٍّ وعدد | `journald` بإعدادٍ عامّ |
| التراجع | **تغييرُ وسمِ صورةٍ** — حتميّ | إعادةُ تثبيتٍ في venv |
| الكلفة | طبقةُ حاوياتٍ + ذاكرتُها | أخفّ |
| **الحاجز** | `sudo` غيرُ متاحٍ الآن | `sudo` غيرُ متاحٍ الآن **+** Postgres ساقط |

**الميلُ الأوّليّ: Docker Compose** — لأنّه **يتجنّب لمسَ خدمتَي النظام
معاً** (Python وPostgreSQL)، وهو عينُ ما طُلب. **وليس قراراً** حتّى يثبت
البندان ①②③.

## ٣) الشكلُ المعماريّ

```
المتصفّح ──HTTPS──► Hub (PHP على المضيف)
                         │
                         ▼  127.0.0.1:4000  ← منشورٌ على loopback فقط
              ┌──────────────────────────────────┐
              │  شبكةُ Docker خاصّة: litellm_net │
              │                                  │
              │   [litellm] ◄──────► [postgres]  │
              │       │              بلا ports:  │
              └───────┼──────────────────────────┘
                      ▼ HTTPS صادر
              مزوّدو النماذج (المرحلة ٢)
```

- **LiteLLM**: `ports: ["127.0.0.1:4000:4000"]` — لا `0.0.0.0` ولا نطاقَ عامّ.
- **PostgreSQL**: **لا `ports:` البتّة** — يُبلَغ بالاسمِ داخلَ الشبكةِ وحدَها.
- **شبكةٌ خاصّةٌ** معرَّفةٌ بالاسم، لا الشبكةُ الافتراضيّة.
- **لا جدارَ يُفتَح، ولا reverse proxy، ولا DNS.**

### B1 بالتفصيل — وتصحيحُ استنتاجٍ خاطئ

| المحاولة | الردّ | القراءة |
|---|---|---|
| `sudo -n -l` | `sudo: a password is required` | **فُسِّر خطأً** بأنّه دليلُ عضويّةٍ في sudoers |
| `sudo` بكلمةِ المرور | **`lynomia is not in the sudoers file`** | **الحقيقة: لا عضويّةَ البتّة** |
| `getent group docker` | `docker:x:990:` | المجموعةُ **فارغة** — لا أحدَ يصل العفريتَ بلا root |

**ولماذا ضلّ الاستنتاجُ الأوّل؟** لأنّ `sudo` يطلب كلمةَ المرورِ **قبل** فحصِ
سياسةِ sudoers عمداً — كي لا يكشف من هو مُخوَّلٌ ومن ليس. فطلبُ الكلمةِ **ليس
دليلَ تخويل**، وقراءتُه كذلك كانت قفزةً من صنفِ `.cpanel.yml` نفسِه: أثرٌ ظاهريٌّ
فُسِّر حالةً داخليّة.

**والطريقُ الوحيد: `root` مباشرةً** — من مزوّدِ الـVPS (بريدُ التفعيل · إعادةُ
تعيينِ كلمةِ root · VNC) أو من لوحةِ Webuzo Admin (`:2005`) ببيانات root.
وحينها **لا `sudo` أصلاً**: الأوامرُ تُنفَّذ بلا بادئة.

**ويبقى `lynomia` خارجَ مجموعةِ docker عمداً** — عضويّتُها تكافئ root عمليّاً،
فكلُّ أمرٍ يمرّ بـroot موثَّقاً بدل صلاحيّةٍ دائمةٍ صامتة.

**ولا يُكتَب `docker-compose.yml` قبل رفعِ B1–B4**: ملفٌّ يثبّت وسماً لم يُتحقَّق
منه، ويفترض عفريتاً لم يُجرَّب، **وعدٌ لا خطّة**.
