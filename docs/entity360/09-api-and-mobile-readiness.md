# ٠٩ — الـAPI وجاهزيّةُ الجوّال (§86–89)

## القرار: لا API 360 مونوليثيّ

المصادرُ المرجعيّةُ لكلِّ علاقةٍ **مغطّاةٌ سلفاً** بمساراتِ `/api/v1` القائمة (CRUD الوحدات + الملخّصات):
- الأصول/المحطات/الموظفون: `GET /api/v1/{module}` و`/{id}` (بحقولهم المصرَّحة).
- تخصيصُ الأصل↔المشروع: `GET /api/v1/projects/{id}/assets` · `/assets/{id}/projects` (الطور السابق).
- الرسم: يُقدَّم داخليّاً؛ العقدُ والحوافُّ نفسُها متاحةٌ عبرَ الوحدات.

§86 يقول صراحةً: **لا رَدَّ مونوليثيّاً ضخماً إن غطّت المساراتُ القانونيّةُ المعلومةَ.** فلم يُضَف مسارُ 360 مركّبٌ —
الجاهزيّةُ عبرَ العقدِ المشترك القائم. أيُّ تحسينٍ مستقبليٍّ يكون **إضافيّاً** (§88).

## OpenAPI (§89)

لم تُضَف مساراتٌ في هذا الطور — المواصفةُ تُولَّد لا تُحرَّر (`php artisan hub:openapi`)، وتتغيّر
حقلُ النسخةِ فقط مع رفع `VERSION`.

## الجوّال (§88)

الجوّالُ الأصيلُ **مؤجَّل** — لا واجهةَ Flutter/iOS/Android. لا WebSockets/Redis. نماذجُ القراءةِ
(`Employee360`/`Station360`/`Asset360`) صنعتُها القراءةُ الخادميّةُ للويب، وهي جاهزةٌ لإعادةِ الاستعمالِ
لاحقاً عبرَ الطبقةِ نفسِها إن لزم — دون التزامٍ الآن.
