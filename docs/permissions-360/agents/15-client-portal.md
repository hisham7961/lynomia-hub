# 15 — بوّابة العميل

> وكيلُ تدقيقٍ للقراءة فقط (Permissions 360 · المرحلة 0). مصدرُه سيرُ التدقيق `wf_8fdd85b1-7b4`.

## الخلاصة

Audited the entire client account-type boundary: PortalGuard (web) + MobilePortalGuard (mobile) whitelists, ClientPortalController/MobileClientPortalController + the shared ClientPortalData reader, ClientMemberController/MobileClientMembersController, PortalController (employee/me), and every client-reachable mobile surface (resource CRUD, sync, search, files, comments, notifications, context/bootstrap/schema). The dedicated portal readers are correctly fail-CLOSED (hub_client_ids()??[], Document::scopeVisibleToClient => whereRaw('1=0')), search/files/comments/schema are correctly capped to MODULE_ALLOW via clientModuleAllowed, notifications/DM are user_id-scoped, and MobileClientPortalController delegates only to the isolated readers. HOWEVER the boundary is NOT fully matrix-independent as the doctrine claims: (1) portal.employee is inside the portal.* whitelist and defers entirely to the hr:v matrix bit, giving a contaminated client the full internal HR-360 while /m/hr is structurally blocked; (2) hub_scope fails OPEN when hub_client_ids()/hub_company_ids() return null (a client with zero ACTIVE memberships), so the generic module engine (/m/{projects,engagements,fin}, mobile.resource/sync/files) loses tenant isolation there; (3) context/bootstrap leak the whole internal companies list (names+count) to any client with no matrix contamination at all; (4) /m/fin ignores the portal's sales-only kind filter and column curation. Client internal-leak count is NOT zero.

## اختبارات مطلوبة

- Client account (account_type=client) with role carrying hr:v hits GET /employee/{id} => assert 404 (must NOT reach employee-360). Regression for PortalGuard whitelist narrowing.
- Client account with role carrying hr:v hits GET /employee/{id}?tab=reports|assets|systems => assert 404, proving no HR tab is reachable via the portal route.
- Client account whose ONLY client_membership is suspended (revoked), role contaminated with projects:v, hits GET /m/projects and GET /api/mobile/v1/projects => assert zero rows (fail-closed), not all-tenant rows.
- Same revoked client with fin:e hits PUT/DELETE /api/mobile/v1/fin/{id} of another tenant => assert 404 (hub_scope fail-closed on empty active set).
- Any client account hits GET /api/mobile/v1/context and /bootstrap => assert companies dimension is empty/absent and count=0 (no internal company names/count leaked).
- Client with empty active memberships hits GET /api/mobile/v1/context => assert clients dimension returns zero rows (not the full client roster).
- Active client with fin:v hits GET /m/fin => assert only CLIENT_INVOICE_KINDS rows and no cost/purchase columns are serialized (parity with portal invoice reader).
- Client account hits GET /api/mobile/v1/search?q=<internal record title> => assert results exclude every module outside {engagements,projects,fin} (already-passing guard; lock as regression).
- Internal user with clients:e but without the new clients.members.manage key hits POST /clients/{client}/members => assert 403 once the fine-grained key lands.
- Client with any/no role hits GET /portal, /api/mobile/v1/portal/* with an id belonging to another client => assert 404 (IDOR guard on ClientPortalData findOrFail).
