# 03 — واجهات API وخلفيّة الجوّال

> وكيلُ تدقيقٍ للقراءة فقط (Permissions 360 · المرحلة 0). مصدرُه سيرُ التدقيق `wf_8fdd85b1-7b4`.

## الخلاصة

Audited routes/api.php + all app/Http/Controllers/Api/* (V1Controller, Mobile{Auth,Activation,Context,Work,Comm,Collab,Resource,Sync,File,Push,ClientPortal,ClientMembers,Reports}Controller, ReportsApiController, AssetProjectApiController, Endpoint{Enroll,Protocol}Controller) and middleware ApiAuth/MobileSessionAuth/MobileContext/MobilePortalGuard/EndpointSignature. Headline: the surface is unusually well-secured — one shared authz engine (hub_can/hub_scope/hub_field_mode), per-op token scoping via resolveApi, structural client isolation via MobilePortalGuard mirroring web PortalGuard, and shared services (CommentService::guardTarget, AttachmentService::guardRecord, DmService, ClientPortalData) give strong web↔API/mobile parity. Verified defects are narrow: (1) two /api/v1 controllers (ReportsApiController::teamDaily, AssetProjectApiController) check hub_can but skip token-scope (tokenAllows) enforcement that every other /api/v1 data endpoint applies, breaking the documented "مفتاح مقيد لا يتجاوز قيده" invariant; (2) the generic client-reachable CRUD/sync/api-v1 path for fin/projects/engagements returns invoice kinds and internal columns that the dedicated ClientPortalData path deliberately curates away (kind∈sales/receipts + client-safe column select), relying entirely on per-role field_mode config for internal-column safety. No uncovered routes, no missing middleware, no DM/notification cross-user leaks, no IDOR in mobile CRUD/files/endpoint-commands.

## اختبارات مطلوبة

- Token-scope on teamDaily: mint an ApiToken with scopes='projects:v' for a user who has hr:v; assert GET /api/v1/reports/daily returns 403 INSUFFICIENT_SCOPE (currently returns 200 with team HR data). Fix ReportsApiController::teamDaily, then assert 403.
- Token-scope on AssetProject writes: mint ApiToken scopes='tickets:v' for a user with assets:e+projects:v; assert POST /api/v1/projects/{id}/assets and POST /api/v1/asset-project/{id}/end return 403 INSUFFICIENT_SCOPE (currently succeed). Also assert GET projects/{id}/assets is 403.
- Client fin curation parity: create a client account whose role has fin:v; seed a fin document with kind='expense'/'purchase' and internal-only columns for that client_id; assert GET /api/mobile/v1/fin, GET /api/mobile/v1/sync/fin, and GET /api/v1/fin do NOT return non-sales/receipt kinds nor internal columns (must match ClientPortalData::invoiceRows projection). Repeat for projects/engagements internal columns.
- Negative control (no regression): an unscoped token (scopes='' or '*') and an internal user with hr:v/assets:e still get 200 on the same endpoints after the fix.
- Metrics approval parity (optional/P3): configure hub_needs_approval true for a module's 'e'; assert POST /api/v1/metrics behavior matches the intended policy (either 202/queued or documented-exempt).
- Cross-user DM/notification isolation regression guards: assert GET /api/mobile/v1/dm/threads/{other}/messages and notifications/{id}/read return 404 when auth is not a party/owner — lock in current correct behavior against future refactors.
- Client boundary on generic api-v1: assert a client account calling GET /api/v1/{internal_module} (module not in PortalGuard::MODULE_ALLOW) receives 404 RESOURCE_NOT_FOUND, confirming resolveApi client fence stays intact.
