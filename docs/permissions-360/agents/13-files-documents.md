# 13 — الملفّات والمستندات والإعلام

> وكيلُ تدقيقٍ للقراءة فقط (Permissions 360 · المرحلة 0). مصدرُه سيرُ التدقيق `wf_8fdd85b1-7b4`.

## الخلاصة

Audited the files/documents/media surface: AttachmentController + shared AttachmentService (single authz engine for web+mobile), FileController (path-served module files), UploadChunkController, InboxDocController, DataRoomController (external shares), MediaCenterController, EsignController (internal + public token signing), MobileFileController, and the client-portal document readers (ClientPortalData / MobileClientPortalController). Headline: the core attachment download/stream/preview/zip paths are consistently gated by AttachmentService::guardRecord (hub_can(module,'v') + hub_scope->findOrFail), so there is NO general download IDOR — a user who cannot view the parent record cannot fetch its bytes on web or mobile, and infected files (av_status) plus non-inline MIMEs are correctly blocked with nosniff/CSP. Verified defects are narrow: (1) FileController::mayRead's inbox_documents branch grants file access on the inboxdocs/files flag alone WITHOUT the company scoping that InboxDocController itself enforces — a cross-company leak of inbox document bytes to a scoped user who obtains the (random) path; (2) attaching/uploading files onto a record requires only module VIEW ('v'), a read->write boundary crossing with no separable key. Public esign verifyDoc correctly redacts signer PII (id_no/IP/selfie/agent gated behind $evidence). DataRoom external shares are token+optional-password gated with watermark/no_download fail-closed. Main structural gap: view-record, download-bytes, attach-file, and share-externally are all collapsed onto module 'v' (+ the broad secrets flag for sharing) with no fine-grained separation.

## اختبارات مطلوبة

- Company-A-scoped user holding inboxdocs 'v' receives 403/404 when fetching a company-B inbox document via GET files/{path} (regression for the FileController inbox scoping leak); a company-A inbox doc and a NULL-company inbox doc still succeed.
- Download/stream/zip enforce guardRecord on both web and mobile: user without module 'v' -> 403; attachment whose record is out of hub_scope -> 404 (findOrFail); infected av_status -> 423; non-inline MIME on stream -> 415.
- After adding documents.attach: a view-only ('v' without attach) principal is denied att.store / mobile files attach / upload-complete; a principal with the attach key succeeds — asserted on an HR record they can view.
- DataRoom share.file: password-protected link without unlock session -> 403; no_download link forces watermarked inline for bitmap/PDF and returns 403 for ?dl=1 and for non-inline types.
- Public esign sign.verify.doc (QR) and client copies render the contract but DO NOT emit signer id_no / signed_ip / selfie / agent (evidence gated), while internal esign.doc/certificate do — asserted at the response body level.
- Signed-copy PDF archived as an Attachment on module=contracts (EsignController archiveSignedCopy) is downloadable only by a user who can view the linked contract (guardRecord contracts 'v') and returns 404 for a user out of the contract's scope.
