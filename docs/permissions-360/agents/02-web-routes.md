# 02 — مسارات الويب والمتحكّمات

> وكيلُ تدقيقٍ للقراءة فقط (Permissions 360 · المرحلة 0). مصدرُه سيرُ التدقيق `wf_8fdd85b1-7b4`.

## الخلاصة

Inventoried authorization for all WEB routes (609-route dump + routes/web.php + 119 controllers in app/Http/Controllers/Web). Nearly every route carries only [web|auth]; real authorization lives in controllers and is applied with remarkable discipline: a per-controller gate() or per-method abort_unless(hub_can|hub_flag|hub_is_owner) plus hub_scope()->findOrFail() for record isolation, hub_field_mode for fields, exportBelt/hub_require_stepup for high-impact actions, and PortalGuard as a global whitelist client boundary. The generic ModuleController::resolve() gates every CRUD op (hub_can + hub_scope) and strips internal artifacts for client accounts; AttachmentService.guardRecord, CommentService.guardTarget, ConversationController.guardConversation, ApprovalService.decide all centralize authz correctly. Closure routes (company/client switch, demo) are gated. Headline: the code is strongly secured with a single engine; the one genuine authorization defect is OversightController — the most sensitive read in the system (surveillance of ALL private channel + DM messages) is gated by a role-NAME string equality against a setting (raw_role), not an assignable permission, and roles.name has no unique constraint. Secondary: the monitor and exp flags are coarse (one flag unlocks unrelated sensitive dashboards / all-module export), and PortalGuard whitelists modules but not HTTP verbs so client accounts can reach m.* mutation routes on allowed modules (op-gating delegated entirely to the role matrix).

## اختبارات مطلوبة

- OversightController: a user whose role.name happens to equal collab.oversight_role but who was never intentionally granted oversight (e.g. a second role cloned with the same name, or a role renamed to the configured string) must NOT reach oversight.index/oversight.show once gating moves to a flag/matrix key — assert 403 before and 200/allowed only for the flag holder.
- OversightController: with collab.oversight_role empty, every account including owner gets 403 on oversight.index (regression guard).
- hub_monitor split: a role granted analytics.workforce.view but not analytics.financial.view gets 200 on WorkforceController and 403 on CostController (project P&L).
- Export granularity: a role with attend.export but not payroll.export can export m/attend but gets 403 on m/payroll export and on m/hr export of salary columns.
- PortalGuard: a client account (account_type=client) whose role matrix has projects:e/a/d still receives 404 on POST m/projects, PUT m/projects/{id}, DELETE m/projects/{id}, POST m/projects/{id}/status, POST m/projects/bulk (write verbs blocked at the guard, not just the matrix).
- PortalGuard regression: client account still reaches GET m/projects and GET m/projects/{id} (read) and portal.*/profile.*/logout.
- Cross-check (should stay green): every admin/* owner-only route returns 403 for a non-owner with a fully-populated matrix but no is_owner; m/{module}/{id}/secret returns 403 without secrets/copySec flag; attachment download/preview by raw id returns 404 for a record outside the caller's hub_scope.
