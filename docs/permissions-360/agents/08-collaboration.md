# 08 — التعاون والمحادثات

> وكيلُ تدقيقٍ للقراءة فقط (Permissions 360 · المرحلة 0). مصدرُه سيرُ التدقيق `wf_8fdd85b1-7b4`.

## الخلاصة

Audited CollaborationController, ConversationController, DmController, GroupController, MessageSearchController, MinutesController, MessagingController plus the shared engine (Conversation model, DmService, CommentService::guardTarget, CollaborationRail) and both the web (ClientPortalController) and mobile (MobileCollabController, MobileCommController, MobileClientPortalController) surfaces. Authority is overwhelmingly PARTICIPATION_GOVERNED: channels/rooms/groups gate on conversation_members via ConversationController::guardConversation (membership + company/client scope + record-thread module-view + post/manage role), DMs gate on DmController::dmReachable (company intersection) with thread_key derived server-side from auth()+other (F8), and search is membership/party/company-scoped. The client boundary is hard: PortalGuard (web whitelist) and denyClient()/MobilePortalGuard (mobile) keep clients out of every internal collab route, and client rooms surface only through ClientPortalData with an audience∈{client,both} + internal-message filter. MinutesController::extract is the one matrix-permission surface (meetings:e + decisions:a + tasks:a) and is correctly gated; MessagingController is owner-only. Two real gaps: (1) client-room membership is the ONLY thing scoping portal conversation reads — the client_id fail-closed filter the rest of ClientPortalData applies is absent, and ConversationController::addMember does no audience/client-boundary validation, so an internal owner/moderator adding the wrong client exposes another client's room cross-client; (2) mobile comment reaction (guardTarget 'feed' branch) is not company-scoped, letting a reaction+notification land on a cross-company feed post.

## اختبارات مطلوبة

- Cross-client room isolation (fail-first): internal moderator of Client A's audience=client conversation adds a User belonging to Client B; assert Client B receives 404/empty from portal.conversation, mobile portal/conversations/{id}, and portal.conversations list does NOT include Client A's room (client_id scope enforced in ClientPortalData::conversationRows/Detail).
- addMember boundary validation: assert addMember returns 422 when adding a client account to an audience=internal room, and when adding a client whose client_id != conversation.client_id to an audience∈{client,both} room.
- Feed react scope: a user in company X toggles a reaction (web CommentController::react and mobile commentReact) on a feed comment whose company_id is company Y (not in the user's scope); assert 404/403 and that no react row and no notification are created.
- Non-member 404 invariant: for a channel the caller is not a member of, assert 404 on conversations.show, conversations.since, conversations.typing, and mobile conversations/{id}/since + channelTyping (guardConversation membership).
- Client boundary: a client account is denied (404) on conversations.*, dm.*, groups.*, collab.center, search.messages, conversations.join (PortalGuard + abort_if hub_is_client) and on mobile collab endpoints (denyClient).
- Internal-message confidentiality: an internal-flagged channel message in a client room is never returned by ClientPortalData::conversationMessages (web + mobile portal), while it IS visible to internal members via conversations.since.
- DM thread privacy (F8): user A cannot retrieve or poll a B<->C thread by supplying B and C ids — mobile dmMessages/dmSince/dmMarkRead rebuild thread_key from auth()+{user} only, and dmReachable out-of-scope returns 404 with no existence disclosure.
- Last-owner + rank invariants: setRole/removeMember cannot demote/remove the sole owner and a moderator cannot act on a role >= their own.
