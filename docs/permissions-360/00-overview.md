# Permissions 360 — نظرةٌ عامّة

> **الهدف:** كلُّ ما يراه مستخدمٌ أو يبلغه أو ينفّذه أو يصدّره أو يعدّله أو يعتمده أو يبحثه أو
> يكتشفه أو يعدّه — **يُفسَّر بمنطقِ التوثيق**. لا رؤيةَ بلا تفسير، ولا إجراءَ بلا صلاحيّة،
> ولا آليّةَ صلاحيّةٍ خفيّة، ولا توثيقَ في الواجهةِ وحدها، ولا تجاوزَ مسارٍ/API.

## المبدأ الحاكم — محرّكٌ واحد لا ثانٍ

Lynomia يملك بنيةَ توثيقٍ ناضجة: `hub_can` (المصفوفة) · `hub_flag` (الرايات) · `hub_scope`/
`hub_company_ids`/`hub_client_ids` (النطاق) · `hub_field_mode` (الحقول) · `PortalGuard` (حدُّ
العميل) · `PermissionInspector` (طبقةُ قراءة) · `RoleController` (محرّرُ الأدوار) ·
`InformationArchitecture` (التنقّل) · `FeatureRegistry` (توافرُ القدرة ≠ صلاحيّة).

Permissions 360 **يوسّع ولا يستبدل.** لا محرّكَ ACL ثانٍ، ولا جدولَ صلاحيّاتٍ منافس، ولا `can()`
ثانٍ، ولا محرّكَ تنقّلٍ/حقولٍ/عميلٍ منفصل.

## الاكتشافُ الجوهريّ (يحدّد المعمار)

`hub_can($user, $module, $op)` يقرأ `matrix[$module][$op]` لـ**أيِّ** سلسلةِ `op` — لا لـ`v/a/e/d`
فقط. إذن الصلاحيّةُ الدقيقةُ = مفتاحُ `(module, action)` مُسمّى في **المصفوفةِ نفسِها**
(`hr.salary.view`, `projects.fin.view`, `attend.export`, `updates.review`…)، بلا تغييرِ محرّك ولا
جدولٍ جديد. المحاورُ الأربعةُ `v/a/e/d` تبقى كما هي (توافقٌ خلفيّ). *لكنّ* محرّرَ الأدوار
(`RoleController::data()`) يبني المصفوفةَ من `v/a/e/d` فقط ويمسحُ أيَّ مفتاحٍ مُسمّى عند الحفظ —
فالتمكينُ الحقيقيُّ = تعليمُ المحرّرِ والمُفسِّرِ المفاتيحَ الدقيقةَ من **كتالوجٍ مُقنَّن**.

## الخيوطُ الكبرى من التدقيق (تقودُ المراحلَ التالية)

1. **راياتٌ عريضةٌ تفرِّطُ في الرؤية** (جوهرُ شكوى المالك):
   - `monitor` = ~15 لوحةً تحليليّةً + بياناتُ الأداء الفرديّة + مركزُ الأصولِ الرقميّة (خزنة) — بمفتاحٍ واحد.
   - `exp` = تصديرُ **كلِّ** وحدةٍ يراها المستخدمُ — بلا بُعدِ وحدة.
   - `approve` = اعتمادُ الرواتبِ **و**المشترياتِ **و**كلِّ الموافقاتِ — بمفتاحٍ واحد.
   - `secrets`/`copySec` = كشفُ الأسرارِ (و`copySec` مسربٌ للكشفِ لا للنسخِ فقط).
2. **تسريباتُ تبويباتِ 360**: تبويبُ الأصولِ في مشروع 360، وتبويبُ المشاريعِ في أصل 360، وتبويبُ
   النشاطِ/التقاريرِ — تظهرُ بلا `hub_can` للوحدةِ المعنيّة.
3. **تسريباتُ حقلٍ عبر الـAPI**: `V1Controller::shape` يمرّرُ عمودَ `meta` غيرَ المعلَن.
4. **IDOR عبرَ الشركات** في `ReportsController::finalize` (يستعملُ `hub_company_scope` الجلسيّ لا
   `hub_scope` الدوريّ).
5. **توثيقٌ باسمِ الدور**: `OversightController::isOversightOfficer` يطابقُ اسمَ الدورِ نصّاً.
6. **حدُّ العميلِ يعتمدُ على `hr:v`** في `portal.employee` (مصفوفةٌ ملوّثةٌ تخترقه).

## خارطةُ المراحل

- **المرحلة 0 (هذه):** تدقيقُ 20 ورشةً (قراءةٌ فقط) → جردٌ + تصنيفٌ + نتائج + إصلاحُ العيوبِ المُثبَتة
  (P1 + راية الرقابة) إثباتاً لا ادّعاءً.
- **المرحلة 1:** التصنيفُ القانونيُّ + كتالوجُ الصلاحيّاتِ المُقنَّن (`config/hub_permissions.php`) +
  توسيعُ `hub_can`/`PermissionInspector`/محرّرِ الأدوار للمفاتيحِ الدقيقة — بلا محرّكٍ ثانٍ.
- **المرحلة 2:** فرضُ المفاتيحِ الدقيقةِ عند السطوحِ الحقيقيّةِ (فكُّ الرايات العريضة، إغلاقُ تسريباتِ
  360/الحقول/العدّ) — كلٌّ باختبارٍ يفشلُ أولاً.
- **المرحلة 3:** مركزُ إدارةِ الصلاحيّات (محرّرُ الأدوارِ الهرميّ القابلُ للبحث) + ترقيةُ المُفسِّر.
- **المرحلة 4:** بوّابةُ التغطيةِ (CI) + الهجرةُ (بلا توسيعٍ صامت) + اختباراتُ الشخصيّاتِ والخصومة +
  التوثيقُ الكاملُ + المحرّكان أخضران + رفعُ النسخة.
