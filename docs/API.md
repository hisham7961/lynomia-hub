# Lynomia Hub — REST API v1

كل الطلبات تتطلب مفتاحاً تُنشئه من **حسابي ← مفاتيح API**، ويُرسل في الترويسة:

```
Authorization: Bearer lyn_xxxxxxxxxxxx
Accept: application/json
```

**المفتاح يحمل صلاحيات صاحبه نفسها**: مصفوفة الدور، نطاق المشاريع، والموافقات المُلزِمة
(العمليات المحمية تُرفض بـ 409 وتُنفذ من الواجهة). كل كتابة تُسجل في التدقيق باسم صاحب المفتاح.
حد المعدل: ١٢٠ طلباً بالدقيقة لكل مفتاح (و٣٠٠ لكل عنوان شبكة) — الترويسات `X-RateLimit-Limit`/`X-RateLimit-Remaining`،
وعند التجاوز `429` مع `Retry-After`. كل رد يحمل ترويسة `X-Request-Id` (وتُعاد في جسم كل خطأ باسم `request_id`) — أرفقها عند طلب الدعم،
وترويسة `X-API-Version: 1` تُعلن إصدار العقد.

> **المواصفة الآلية (OpenAPI 3.1):** `GET /api/v1/openapi.json` — مولَّدة من سجل الوحدات نفسه ومقصورة على ما يراه مفتاحك
> (وحدات ونطاقات وحقول دورك). النسخة الكاملة في `docs/openapi.json` (تُحدَّث بـ`php artisan hub:openapi`).

## تقييد المفاتيح (اختياري لكنه مستحسن)

عند إنشاء المفتاح من **حسابي ← مفاتيح API** تستطيع:

- **نطاقات**: `tickets:va, projects:v` — وحدة:عمليات (`v` عرض، `a` إضافة، `e` تعديل، `d` حذف).
  فارغ أو `*` = كامل صلاحيات الحساب. المفتاح **لا يتجاوز صلاحيات صاحبه أبداً** — النطاق تضييق فقط.
  الطلب خارج النطاق يُرفض 403.
- **قائمة IP**: `1.2.3.4, 10.0.0.0/8` — عناوين مفردة أو CIDR. فارغة = من أي مكان.
- **انتهاء صلاحية** بالأيام، و**تدوير** 🔄 من نفس الشاشة: قيمة جديدة بنفس الاسم والنطاقات،
  والقديمة تتوقف فوراً.

## Idempotency (منع التنفيذ المزدوج)

أرسل ترويسة `Idempotency-Key: <قيمة-فريدة-من-عندك>` مع أي `POST` إنشاء.
إعادة نفس الطلب بنفس المفتاحين (مفتاح API + Idempotency-Key) خلال يومين تعيد **الرد المخزن
نفسه** بلا إنشاء ثانٍ، مع ترويسة `X-Idempotent-Replay: true` — مثالي لإعادات n8n التلقائية.

## اختيار الحقول

`?fields=name,email` على القائمة والسجل الواحد: يعيد `id` + المفاتيح المطلوبة فقط —
ردود أخف لتكاملات لا تحتاج كل الأعمدة.

## الفرز والترشيح (القوائم)

| معامل | المعنى |
|---|---|
| `sort=name` / `sort=-name` / `sort=amount&dir=asc` | فرز بمفتاح حقلٍ من حقول الوحدة الظاهرة لدورك، أو `created_at`/`updated_at`. البادئة `-` تنازلي. ما خرج عن القائمة البيضاء يُتجاهَل (الفرز الافتراضي `created_at` تنازلياً) ويُقال في `meta.sort` |
| `q=` · `status=` | بحث نصّي وترشيح بالحالة (كما كانا) |
| `f[clientId]=<uuid>` | ترشيح بمرجع — كما في شاشة القائمة (`company_id`/`project_id` الضمنيان أيضاً) |
| `fl[0][f]=amount&fl[0][o]=gt&fl[0][v]=1000` | مرشِّحات متقدّمة (حتى ١٠ شروط بمنطق «و») — العوامل: `has eq neq gt lt before after empty nempty` |
| `created_from=2026-01-01` · `created_to=2026-01-31` | نافذة الإنشاء (تاريخ) |
| `updated_since=2026-01-31T10:00:00%2B03:00` | كل ما عُدّل بعد لحظة — للمزامنة التزايدية (رمّز `+` في الرابط) |
| `trash=1` | السلة (يتطلب صلاحية الحذف) |

الردّ يحمل `meta` بجانب المفاتيح القديمة: `{page, per, total, last_page, has_more, sort, dir, filters}`.
الحقول المحجوبة عن دورك لا تُفرَز بها ولا تُرشَّح ولا تظهر — كما في الواجهة تماماً.

## التعديل الجزئيّ والقفل التفاؤليّ

- `PUT /{module}/{id}` **استبدال كامل** (الحقل الغائب يُفرَّغ) — كما كان.
- `PATCH /{module}/{id}` **تعديل جزئيّ**: يكتب الحقول المُرسَلة وحدها ويُبقي البقية. مفتاحٌ من خارج حقول الوحدة يُرفض بـ`422`.
- كل ردّ سجلٍّ يحمل `ETag: "<version>"`. أرسل `If-Match: "<version>"` (أو `_version` في الجسم) مع PUT/PATCH؛
  إن عدّله غيرك بعدها تحصل على `409 VERSION_CONFLICT` مع `details.current_version` — فلا يُدهَس تعديلٌ بصمت.
  غياب الترويسة لا يمنع (توافقٌ مع العملاء القدامى).

## ما لا يخرج من الـ API أبداً

كل ردّ يحمل سجلاً — **قراءةً وكتابةً** (`GET` و`POST` و`PUT`) — يمرّ بمرشّح واحد يُسقط:

- **حقول الأسرار** (نوع `sec` كخانة السرّ في الخزنة) عن كل مفتاح لا يملك صاحبه
  علم «رؤية الأسرار» (`secrets`) أو «نسخ الأسرار» (`copySec`) أو صفة المالك —
  تماماً كما تُقنّعها الواجهة بـ `••••••`. تُحذف الخانة **حذفاً لا تقنيعاً**، فإعادة
  إرسال السجل كما هو بـ `PUT` لا تدهس السرّ بقيمة قناع.
- **الحقول المخفية** بصلاحيات مستوى الحقل لدور صاحب المفتاح.

من يملك العلم يستلم القيمة كاملةً كالمعتاد.

## نطاق المفتاح على التقارير والفهرس

المفتاح **بلا نطاق** (فارغ أو `*`) يصل كل شيء كما كان. أما المفتاح **المقيّد بنطاقات**
فيلزمه إدراج ما يحتاجه صراحةً:

| المسار | النطاق المطلوب |
|---|---|
| `GET /api/v1/reports/progress/{id}` | `projects:v` |
| `GET /api/v1/reports/health` | `reports:v` |
| `GET /api/v1/modules` | يُدرج الوحدات التي يسمح بها النطاق فقط |

> ⚠️ **إن كان لديك مفتاح مقيّد يستدعي التقارير**، أضف `projects:v` أو `reports:v` إلى نطاقاته
> من **حسابي ← مفاتيح API**، وإلا استقبلت 403.

## نقاط عامة

| الطلب | الوصف |
|---|---|
| `GET /api/v1/me` | هوية صاحب المفتاح ودوره |
| `GET /api/v1/modules` | الوحدات المتاحة له بحقولها وصلاحياته عليها |
| `GET /api/v1/reports/progress/{projectId}` | نسبة إنجاز مشروع بتفاصيل مكوناتها |
| `GET /api/v1/reports/health` | صحة الشركة (مالكون فقط) |

## وحدات الأعمال (الـ ٥١ كلها)

`{module}` = مفتاح الوحدة من `GET /modules` (مثل `clients`، `tasks`، `fin`…)

| الطلب | الوصف |
|---|---|
| `GET /api/v1/{module}?q=&status=&page=&per=&fields=` | قائمة مرقمة (per ≤ 100) مع بحث وفلتر حالة واختيار حقول |
| `GET /api/v1/{module}/{id}?fields=` | سجل واحد |
| `POST /api/v1/{module}` | إنشاء — أرسل الحقول **بمفاتيح السجل** (مثل `nameAr`، `clientId`) بنفس تحقق النماذج |
| `PUT /api/v1/{module}/{id}` | تعديل — **استبدال كامل**: أرسل كل الحقول التي تريد إبقاءها؛ الحقل الغائب يُفرَّغ (اقرأ السجل بـ GET ثم أعد إرساله معدلاً) |
| `DELETE /api/v1/{module}/{id}` | نقل للسلة |

## أمثلة

```bash
# هويتي
curl -H "Authorization: Bearer $TOKEN" https://hub.lynomia.com/api/v1/me

# عملاء فيهم كلمة «الخليج»
curl -H "Authorization: Bearer $TOKEN" "https://hub.lynomia.com/api/v1/clients?q=الخليج"

# إنشاء مهمة (لاحظ: مفاتيح الحقول لا أعمدة القاعدة)
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"title":"مراجعة الفاتورة","projectId":"<uuid>","assigneeId":"<uuid>","status":"جديدة"}' \
  https://hub.lynomia.com/api/v1/tasks

# نسبة إنجاز مشروع
curl -H "Authorization: Bearer $TOKEN" https://hub.lynomia.com/api/v1/reports/progress/<uuid>
```

## الأخطاء — عقدٌ واحد بكود آليّ

كل خطأ على `/api/*` يعود بالشكل نفسه:

```json
{
  "error": "الرسالة العربية",          // مفتاح التوافق القديم — كما كان
  "code": "VALIDATION_FAILED",        // كود آليّ ثابت — عليه يقرّر عميلك لا على النصّ
  "message": "الرسالة العربية",
  "details": { "…": "…" },            // عند توفّرها (أخطاء التحقق بالحقل، النسخة الحالية، النطاق المطلوب…)
  "errors": { "name": ["…"] },        // 422 فقط — الشكل القديم محفوظ
  "request_id": "uuid"
}
```

والترويسة `X-Error-Code` تحمل الكود نفسه. لا تُسرَّب أسماء أصناف داخلية ولا مواضع ملفات.

| HTTP | `code` | المعنى |
|---|---|---|
| 401 | `UNAUTHENTICATED` | مفتاح مفقود/غير صالح/منتهٍ |
| 403 | `FORBIDDEN` | لا صلاحية على الوحدة أو الفعل |
| 403 | `INSUFFICIENT_SCOPE` | نطاق المفتاح لا يشمل `module:op` (في `details`) |
| 403 | `ACCOUNT_RESTRICTED` | الحساب موقوف/مقفل/منتهٍ أو محصور بعناوين شبكة (`details.reason`) |
| 404 | `RESOURCE_NOT_FOUND` | وحدة (`details.kind = module`) أو سجل (`record`) غير موجود أو خارج نطاقك |
| 405 | `METHOD_NOT_ALLOWED` | الطريقة غير مدعومة |
| 409 | `APPROVAL_REQUIRED` | العملية محمية بالموافقات — نفّذها من الواجهة |
| 409 | `VERSION_CONFLICT` | النسخة التي تحملها قديمة (`details.current_version`) |
| 409 | `IDEMPOTENCY_IN_PROGRESS` | الطلب نفسه قيد المعالجة الآن — أعد بعد `Retry-After` |
| 413 | `PAYLOAD_TOO_LARGE` | الحمولة أكبر من المسموح |
| 422 | `VALIDATION_FAILED` | فشل التحقق — التفاصيل في `errors`/`details` |
| 422 | `IDEMPOTENCY_KEY_REUSED` | مفتاح Idempotency أُعيد بطلبٍ مختلف |
| 423 | `LOCKED` | مجمَّد بمفتاح طوارئٍ أمنيّ (سكّ الرموز/التصدير) |
| 428 | `STEP_UP_REQUIRED` | يتطلب تأكيد الهوية (`url` لشاشة التأكيد) |
| 429 | `RATE_LIMITED` | تجاوز حد المعدل — `Retry-After` |
| 500 | `INTERNAL_ERROR` | عطل داخليّ سُجّل تلقائياً — أرفق `request_id` |
| 503 | `MAINTENANCE` | وضع الصيانة — القراءة تمرّ والكتابة تتوقف (`Retry-After`) |
| 503 | `LOCKDOWN` | قفل طوارئ — سطح API معلَّق بالكامل (يرفعه المالك من المتصفح) |
| 503 | `INTEGRATION_UNAVAILABLE` / `SERVICE_UNAVAILABLE` | خدمة خارجية أو داخلية غير متاحة مؤقتاً |

**قاعدة الإعادة:** أعد المحاولة على `429`/`503`/`IDEMPOTENCY_IN_PROGRESS` بعد `Retry-After`؛ ولا تُعد على `4xx` الأخرى (خطؤك أنت).

**الإهمال والإصدار:** المسارات تحت `/api/v1` ثابتة. أي تغيير كاسر يأتي في `/api/v2` مع إبقاء `v1` لفترة انتقال معلنة؛
والمسار المُهمَل يُعلَن بترويستي `Deprecation` و`Sunset` قبل إزالته، ويُدرَج في `x-deprecations` داخل المواصفة.

## Webhooks (الأحداث الصادرة)

اشترك من **الإدارة ← 🪝 Webhooks**: رابط استقبال + قائمة أحداث
(`*` أو `tickets.created` أو `projects.*` أو `*.status` — الأحداث: `created` و`updated` و`status`).

كل حدث يصلك `POST` بجسم JSON:

```json
{
  "event": "tickets.created",
  "module": "tickets",
  "label": "التذاكر",
  "record_id": "uuid",
  "display": "عنوان التذكرة",
  "status_to": null,
  "by": "اسم المنفذ",
  "at": "2026-07-30T12:00:00+03:00",
  "data": { "مفاتيح الحقول من سجل الوحدات": "بلا أسرار وبلا مسارات ملفات" }
}
```

**الترويسات:**

| ترويسة | المعنى |
|---|---|
| `X-Hub-Event` | اسم الحدث مثل `tickets.created` |
| `X-Hub-Event-Id` | معرف فريد — خزّنه وتجاهل أي تكرار له |
| `X-Hub-Signature` | `sha256=hex(hmac_sha256(body, secret))` — تحقق قبل التصديق |

**التسليم:** رد بـ 2xx خلال ١٠ ثوانٍ. الفاشل يُعاد تلقائياً بتباعد
(١ ← ٥ ← ١٥ ← ٦٠ ← ١٨٠ ← ٧٢٠ دقيقة)، وبعد ١٠ إخفاقات متتالية يُوقَف
الاشتراك ساعة ثم يستأنف. سجل المحاولات وإعادة الإرسال اليدوي وزر الاختبار
كلها في صفحة الاشتراك.

**مثال تحقق في PHP عند المستقبل:**

```php
$sig = 'sha256=' . hash_hmac('sha256', file_get_contents('php://input'), $secret);
if (! hash_equals($sig, $_SERVER['HTTP_X_HUB_SIGNATURE'] ?? '')) http_response_code(401);
```
